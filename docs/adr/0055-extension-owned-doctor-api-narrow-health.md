# Extension-Owned Doctor, API Narrow Health

Status: accepted

The full doctor/check setup report should be owned by the extension host, not exposed as a local API `/doctor` endpoint. The extension host can inspect SecretStorage, extension state, tunnel lifecycle, status bar settings, notification settings, Cursor setup confirmation, runtime ownership, and environment boundaries.

The local API should expose only narrow machine-readable health/status endpoints needed by Cursor, the extension supervisor, and the dashboard.

## Consequences

- The doctor command/report lives in `apps/extension` and may aggregate signals from the local API, tunnel manager, auth manager, settings, and dashboard state.
- The local API should expose narrow endpoints such as unauthenticated minimal `/health`, authenticated `/ready`, authenticated `/v1/models`, and possibly an internal `/internal/status` guarded by the generated local API key or extension-private channel.
- The local API should not expose SecretStorage-derived information, full setup diagnostics, notification preferences, status bar preferences, or cross-environment auth-transfer state.
- API health endpoints should report only what the API owns: process health, protocol readiness, auth-handoff readiness state, model list readiness, and recent upstream/protocol error summaries where safe.
- Doctor support exports should be generated by the extension host so redaction policy and environment context are centralized.
- The dashboard should call extension-owned doctor actions, not a public API `/doctor` route.
